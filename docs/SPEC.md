# Спецификация и план работ

Рабочий документ по тестовому заданию (ветка `middle`). Исходные требования — в [README.md](../README.md),
здесь они разложены в проверяемые критерии, зафиксированы архитектурные решения и порядок работы.

Документ ведётся по ходу разработки: отмечаем выполненные пункты, дописываем принятые решения.

---

## 1. Стек

| Что | Выбор | Почему |
| --- | --- | --- |
| Сборка | Vite + `@vitejs/plugin-react` | CRA не поддерживается с 2023 года; Vite — как в основном рабочем проекте |
| Язык | TypeScript | модель данных нетривиальна (цена строкой, размеры массивом ID) — типы ловят это на компиляции |
| Роутинг | `react-router-dom` v7 | нужен для 3 страниц + состояние в URL |
| Состояние корзины | `Context` + `useReducer` | объём состояния мал, внешний стор был бы лишней зависимостью |
| Состояние фильтров | `useSearchParams` | фильтры и так должны жить в URL, дублировать их в память не нужно |
| Стили | CSS Modules | изоляция без дополнительных зависимостей, Vite поддерживает из коробки |
| Проверка слоёв | `eslint-plugin-boundaries` | направление импортов должно проверяться, а не декларироваться |

Абсолютные импорты — `paths` в `tsconfig.json` плюс зеркальный `resolve.alias` в `vite.config.ts`,
чтобы работали пути вида `entities/product`.

**Про миграцию шаблона.** Перевод на Vite + TS — инфраструктурная работа, она идёт **отдельным коммитом
до** генерации кода приложения. Иначе baseline-диф наполовину состоял бы из конфигов, а не из решения задачи.
`src/services/api.js` **не трогаем вообще** — ни содержимого, ни расширения (README ссылается именно на этот
путь, и в дифе файл должен остаться нулевым). Типы описываем рядом, в `shared/api`, которая объявляет
модуль и реэкспортирует его функции уже типизированными. В `tsconfig.json` для этого включаем `allowJs`.

## 2. Архитектура

### 2.1 Выбор и рассмотренные альтернативы

| Вариант | Решение | Обоснование |
| --- | --- | --- |
| **FSD (усечённый)** | **взят** | даёт общепринятый словарь слоёв, реальная переиспользуемость в `entities/product` и `entities/cart` |
| FSD в полном объёме | нет | шесть слоёв с симметричными сегментами на трёх страницах — оверинжиниринг |
| Микрофронтенды | нет | решают организационную задачу (несколько команд, независимые деплои). Здесь нет ни одного из условий |
| Atomic Design | нет | ортогонален FSD, а не альтернатива ему: роль atoms/organisms уже закрывают `shared/ui` и `widgets` |
| Плоская `components/pages/hooks` | нет | рабочий вариант для такого объёма, но не показывает работу со структурой |
| `modules/products`, `modules/cart` | нет | по сути тот же FSD, но без устоявшейся терминологии |

### 2.2 Слои

Слои сверху вниз, импорт разрешён **только вниз**:

```
app → pages → widgets → features → entities → shared
```

Сегменты (`ui`, `model`, `lib`) внутри слайса заводим по факту наличия, а не для симметрии.

```
src/
  services/api.js          # НЕ ТРОГАЕМ — псевдо-API из задания, диф по файлу нулевой
  app/
    index.tsx              # композиция провайдеров и роутера
    providers/             # with-cart.tsx, with-router.tsx + withProviders
    routes.tsx
    styles/                # глобальные стили, reset, переменные
  pages/
    products/              # список товаров
    product/               # детальная
    cart/                  # корзина
    notFound/              # 404 / товар не найден
  widgets/
    header/                # шапка + кнопка перехода в корзину со счётчиком
    productGrid/           # сетка карточек
    productDetails/        # композиция детальной + model/useProductOptions (цвет и размер в URL)
  features/
    productFilters/        # поиск, «в наличии», сортировка (пишут в URL)
    imageGallery/          # переключение изображений без сторонних библиотек
    colorPicker/           # выбор цвета
    sizePicker/            # выбор размера, недоступные заблокированы
    addToCart/             # кнопка добавления
    cartItemControls/      # количество ±, удаление позиции
    promocode/             # поле промокода и расчёт скидки
  entities/
    product/
      model.ts             # селекторы: минимальная цена, доступность, размеры цвета
      ui/productCard/      # index.tsx + styles.module.css
      index.ts
    cart/
      model/               # types, reducer, context, provider, useCart
      lib/storage.ts       # чтение/запись localStorage с валидацией
      index.ts
  shared/
    api/                   # типизированная обёртка над services/api.js + типы домена
    ui/                    # button, input, select, checkbox, spinner, stateMessage
    lib/                   # cn, money, useAsync, useDebouncedValue, useScrollToTop
    config/                # ключи localStorage, маршруты, справочник промокодов
```

**Почему `services/api.js` остаётся на месте.** Задание запрещает менять данные и явно указывает путь к API.
Физически файл не двигаем, чтобы диф не выглядел как правка API; доступ к нему идёт через `shared/api`,
так что слоевая дисциплина не нарушается.

### 2.3 Конвенции

Взяты из рабочего FSD-проекта, чтобы структура была не декларативной, а рабочей.

- **Публичный API слайса.** У каждого слайса есть `index.ts`; снаружи импортируем только из корня
  (`entities/product`), внутренние файлы наружу не торчат. Это то, ради чего слои и вводятся.
- **Границы проверяет линтер.** Подключён `eslint-plugin-boundaries` с правилом `boundaries/dependencies`:
  запрещены импорт вверх по слоям, импорт соседнего слайса и обращение во внутренности слайса мимо `index`.
  Правило проверено на файлах-нарушителях, а не просто прописано в конфиге.
- **Колокация.** Компонент — это папка: `index.tsx` + `styles.module.css` (+ `model.ts`, `helper.ts` при
  необходимости). Никаких общих свалок вида `src/components`.
- **Нейминг** — camelCase для слайсов и папок компонентов, PascalCase для самих компонентов.
- **Провайдеры** — отдельными файлами `app/providers/with-*.tsx`, композиция через HOC `withProviders`.

## 3. Модель данных и её особенности

Структура из `src/services/api.js` (менять её нельзя):

```
product: { id, name, categoryId, brand, colors[] }
color:   { id, name, images[], price: "123.00", description, sizes: number[] }  // sizes — массив ID
size:    { id, name: "XS", number: 44 }
```

Что важно учесть — это источник большинства крайних случаев:

1. **`price` — строка** (`"123.00"`). Считать деньги во `float` нельзя. Парсим один раз в целые копейки
   (`Math.round(parseFloat(price) * 100)`), всю арифметику ведём в целых, форматируем только на выводе.
2. **`color.sizes` может быть пустым** (`[]`) — такой цвет недоступен целиком.
3. **Товар может быть недоступен полностью.** У товара `id: 6` («Пальто») пусты оба цвета —
   он обязан отсеиваться фильтром «в наличии». Это готовый тест-кейс.
4. **`color.id` уникален только внутри товара.** У каждого товара цвета нумеруются с 1, поэтому
   ключ позиции корзины — тройка `productId + colorId + sizeId`, а не один `colorId`.
5. **Количество изображений у цвета — от 1** (у «Худи бежевый» одна картинка).
   Переключатель изображений не должен ломаться и не должен показывать стрелки, когда переключать нечего.
6. **`sizes` из API — справочник.** Кнопки размеров рисуем по полному списку из `getSizes()`,
   доступность определяем пересечением с `color.sizes`.
7. **`getProduct` реджектится с `Error`**, а не резолвит `null`. Отличить «не найдено» от «сбой» по API
   нельзя, поэтому отказ `getProduct` трактуем как «Товар не найден».

### Доменные решения

- **Цена товара в списке** — минимум по **всем** цветам, включая недоступные. README говорит
  «минимальная из его цветов» без оговорок; выделять доступные было бы вольной трактовкой.
- **«В наличии»** — существует хотя бы один цвет, у которого `sizes.length > 0`.
- **Поиск** — по подстроке в `name`, регистронезависимо, с `trim` и дебаунсом ~300 мс.
- **Сортировка** — `asc` / `desc` по минимальной цене. В README опечатка (`decs`); в URL пишем `desc`.

## 5. Состояние в URL

| Страница | Параметры | Пример |
| --- | --- | --- |
| Список | `q`, `inStock`, `sort` | `/?q=фут&inStock=1&sort=asc` |
| Деталь | `color`, `size` | `/product/1?color=2&size=3` |

Параметры по умолчанию в URL не пишем, чтобы ссылка оставалась чистой. Некорректные значения
(несуществующий цвет, недоступный размер) игнорируем и откатываемся к значению по умолчанию —
битая ссылка не должна ронять страницу.

## 6. Порядок работы и коммитов

Требование заказчика: **сгенерированный код — первым коммитом, все последующие изменения — отдельными**,
чтобы был виден вклад разработчика. Историю после этого не переписываем
(никаких `amend`, `rebase -i`, `push --force`).

| # | Этап | Содержание | Статус |
| --- | --- | --- | --- |
| 0 | Документы | `docs/SPEC.md`, `CLAUDE.md` с правилами, `docs/prompts/` | [x] |
| 1 | Инфраструктура | перевод шаблона на Vite + TypeScript, ESLint с границами слоёв, алиасы | [x] |
| 2 | Baseline | вся обязательная функциональность (разделы 4.1–4.4) одним коммитом, как сгенерировано | [x] |
| 3 | URL-состояние | раздел 4.5, п. 1 | [x] |
| 4 | Промокод | раздел 4.5, п. 2 | [x] |
| 5 | Доводка | правки по чек-листу, состояния, доступность, мелочи UX | [x] |
| 6 | Финал | README с описанием решения и запуска | [x] |
| 7 | Ревью перед PR | проверка по осям (баги, стиль, мёртвый код, ассеты), правки по итогам | [x] |

Этапы 0–1 идут до генерации, поэтому этап 2 остаётся чистым кодом приложения без конфигов.
Baseline фиксируется **до** любых ручных правок — даже если что-то работает не идеально. Всё,
что чинится после, попадает в этапы 3+ и тем самым видно в истории.
