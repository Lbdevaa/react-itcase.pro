# CLAUDE.md

Правила работы над проектом для AI-агентов и разработчиков. Полная постановка задачи — в
[README.md](README.md), спецификация и план работ — в [docs/SPEC.md](docs/SPEC.md).

## О проекте

Мини-каталог товаров на React: список товаров, детальная страница, корзина. Данные — из локального
псевдо-API, без бэкенда. Тестовое задание, ветка `middle`.

## Команды

```bash
npm run dev        # dev-сервер Vite
npm run build      # проверка типов + production-сборка
npm run preview    # просмотр собранного бандла
npm run lint       # ESLint, включая правила границ слоёв
```

## Стек

React 18, TypeScript, Vite, react-router-dom v6, CSS Modules. Состояние корзины — `Context` +
`useReducer`, состояние фильтров — в URL через `useSearchParams`.

Новые зависимости не добавляем без явной необходимости: задание оценивает структурность и чистоту, а не
умение подключать библиотеки. Переключение изображений на детальной странице по условию задания должно быть
написано вручную — **сторонние слайдеры запрещены**.

## Архитектура: Feature-Sliced Design (усечённый)

```
app → pages → widgets → features → entities → shared
```

- Импорт разрешён **только вниз по слоям**. Правило проверяется `eslint-plugin-boundaries`, а не
  соблюдается на честном слове.
- Импорты между слайсами одного слоя запрещены. Если примитив нужен соседнему слайсу — поднимаем его
  в слой ниже (обычно в `shared/ui`).
- У каждого слайса есть публичный API — `index.ts` в корне. Снаружи импортируем только из корня слайса,
  во внутренние файлы не лезем.
- Сегменты (`ui`, `model`, `lib`) заводим по факту наличия, а не ради симметрии. Пустых папок нет.
- Компонент — это папка: `index.tsx` + `styles.module.css` (+ `model.ts`, `helper.ts` при необходимости).
  Общей свалки `src/components` не существует.
- Нейминг: camelCase для слайсов и папок компонентов, PascalCase для самих компонентов.

Перед созданием нового компонента проверяем `shared/ui` — дубли примитивов самая частая ошибка.

## Ограничения задания

- **`src/services/api.js` не трогаем.** Ни содержимого, ни расширения, ни расположения — диф по файлу
  должен остаться нулевым. Типизация живёт рядом, в `shared/api`, поверх `allowJs`.
- Структуру данных менять нельзя. В частности — нельзя переносить `sizes` внутрь объектов `colors`.
  Добавлять свои поля (например `hex` для цвета) в собственном коде можно.
- Данные берём только из `api.js`, других источников нет.

## Работа с данными

- **Цена приходит строкой** (`"123.00"`). Считать во `float` нельзя: парсим один раз в целые копейки
  (`Math.round(parseFloat(price) * 100)`), всю арифметику ведём в целых, форматируем только на выводе.
- `color.sizes` — массив **ID размеров**, а не объектов. Полный справочник тянем из `getSizes()`,
  доступность считаем пересечением.
- `color.sizes` может быть пустым — цвет недоступен целиком. Товар может быть недоступен полностью
  (`id: 6`, «Пальто»).
- `color.id` уникален только внутри товара. Ключ позиции корзины — тройка `productId + colorId + sizeId`.
- Изображений у цвета может быть одно — галерея не должна ломаться и не должна показывать стрелки,
  когда переключать нечего.
- `getProduct`/`getProductColor` реджектятся с `Error`, а не резолвят `null`.

## UX-требования

Любая асинхронная операция имеет видимые состояния: загрузка, ошибка, пустой результат. Пустой результат
фильтрации и пустой список — разные состояния с разными текстами. Runtime-ошибок быть не должно,
особенно при старте приложения.

## Правила коммитов

История должна показывать, что именно делал разработчик:

- Первым идёт коммит со сгенерированным кодом — **в том виде, как он сгенерирован**, без ручных правок.
- Все последующие изменения — отдельными осмысленными коммитами.
- Историю не переписываем: без `commit --amend`, `rebase -i` и `push --force`.
- Сообщения на русском, в повелительном наклонении, с типом изменения (`feat`, `fix`, `refactor`, `docs`,
  `chore`).
